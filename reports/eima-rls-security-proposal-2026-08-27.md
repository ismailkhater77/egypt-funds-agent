# مقترح تأمين RLS لطبقة EIMA — 27 أغسطس 2026

## الغرض وحدود الإجراء

أظهر الفحص البنيوي الحي لمشروع Supabase أن جدولي `public.eima_reports` و`public.eima_report_indicators` موجودان في مخطط `public` وميزة **Row Level Security (RLS)** معطلة عليهما. وتحذر وثائق Supabase من أن الجداول المعروضة في `public` ينبغي تفعيل RLS عليها، لأن الوصول من الواجهة قد يمر بأدوار `anon` أو `authenticated`.[1]

هذا المستند **مقترح للمراجعة فقط**. لم يُنفذ أي أمر على قاعدة البيانات، ولم تُنشأ ترحيلة قابلة للتطبيق. وتظل بيانات EIMA الحالية سليمة وغير معدلة: 31 تقريرًا و569 مؤشرًا مرتبطًا بالتقارير.

## نموذج الوصول المقترح

طبقة EIMA هنا بيانات مرجعية يديرها الخادم فقط؛ لا يوجد حقل ملكية مستخدم مثل `user_id`، ولا يستخدم التطبيق الحالي هذه الجداول مباشرة في أي مسار واجهة أو tRPC. لذلك فإن مبدأ أقل الصلاحيات هو **حظر الوصول المباشر من الواجهة تمامًا**، والسماح للعمليات الخلفية ذات `service_role` فقط. تتجاوز مفاتيح الخدمة RLS عند استخدامها من الخادم، ولا يجوز كشفها للمتصفح.[1]

| الدور | القراءة المباشرة من API | الإضافة/التعديل/الحذف المباشر | المبرر |
|---|---:|---:|---|
| `anon` | مرفوض | مرفوض | لا توجد حاجة عامة لبيانات التقرير الخام. |
| `authenticated` | مرفوض | مرفوض | لا توجد واجهة حالية تتطلب وصول المستخدمين لهذه الجداول. |
| `service_role` على الخادم | مسموح | مسموح | الاستيراد الدوري الخلفي والتدقيق الإداري فقط. |
| مستخدم قاعدة البيانات الإداري | حسب صلاحيات Supabase | حسب صلاحيات Supabase | خارج مسار الواجهة، لأغراض التشغيل والإدارة. |

## ترحيلة مقترحة بعد الموافقة الصريحة

بعد موافقة المستخدم، يُحفظ النص التالي في ملف ترحيل تحت `supabase/migrations/` ويطبق بواسطة مسار ترحيلات Supabase المخصص، وليس عبر تنفيذ DDL عشوائي. تُمنح صلاحيات الخدمة صراحة لضمان استمرار المستورد الخلفي، بينما يحرم الدوران المعرضان للواجهة من كل الصلاحيات المباشرة.

```sql
ALTER TABLE public.eima_reports ENABLE ROW LEVEL SECURITY;
ALTER TABLE public.eima_report_indicators ENABLE ROW LEVEL SECURITY;

REVOKE ALL ON TABLE public.eima_reports FROM anon, authenticated;
REVOKE ALL ON TABLE public.eima_report_indicators FROM anon, authenticated;

GRANT SELECT, INSERT, UPDATE, DELETE ON TABLE public.eima_reports TO service_role;
GRANT SELECT, INSERT, UPDATE, DELETE ON TABLE public.eima_report_indicators TO service_role;
```

بمجرد تفعيل RLS، لا يصل أي مفتاح واجهة إلى الصفوف ما لم توجد سياسة؛ لهذا لا يقترح هذا التصميم أي سياسة `SELECT` واسعة مثل `USING (true)`، لأنها ستعيد فتح البيانات دون حاجة تشغيلية.[1] وإذا تقرر مستقبلًا عرض تقارير أو مؤشرات EIMA للمستخدمين، فيجب إضافة واجهة خادمية تقرأ الحد الأدنى من الأعمدة أو سياسة قراءة محددة النطاق، مع مراجعة مستقلة قبل توسعة الوصول.

## خطة التحقق بعد التطبيق

يجب أن تسبق هذه الخطوات أي إعلان إغلاق للملاحظة الأمنية، وأن تُنفذ على قاعدة البيانات الحية دون تغيير محتوى صفوف EIMA.

| الاختبار | النتيجة المطلوبة |
|---|---|
| فحص حالة RLS للجدولين | `rls_enabled = true` لكل منهما. |
| محاولة قراءة عبر `anon` | رفض صلاحية أو صفر صفوف وفق مسار API؛ لا تتسرب البيانات. |
| محاولة قراءة/استيراد من الخادم بـ`service_role` | استمرار القراءة والكتابة الخلفية كما هي. |
| تدقيق العلاقات | 31 تقريرًا، 52,920 صف أداء، 569 مؤشرًا، وصفر صفوف يتيمة كما قبل الإجراء. |
| اختبار تطبيق المشروع | `pnpm test` و`pnpm exec tsc --noEmit` يمران بلا خطأ. |

> لا ينبغي تفعيل RLS بلا هذا التصميم أو دون اختبار لاحق؛ إذ إن تفعيلها بلا سياسات أو صلاحيات مناسبة قد يقطع مسارًا مشروعًا للوصول إلى البيانات.[1]
